# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/). While on 0.x, any minor release may contain breaking protocol or API changes.

## [Unreleased]

### Added

- Directory previews ([ADR-62](docs/decisions.md#adr-62-消息里的本地文件链接在应用内打开html-报告经预览隧道按项目目录提供), [spec](docs/spec/daemon.md#196-目录预览)): a preview can now target a project directory instead of a port. `preview.open { dir }` takes a project name (or `.scratch` for scratch sessions) and the daemon serves that directory's files itself over the same Noise tunnel and preview runtime as dev server previews. It serves files read-only, only inside that directory, and never serves hidden files or directories (`.git`, `.env`, …; the `.anycon/worktrees/<name>/` prefix is allowed so worktree sessions work); it answers `GET` / `HEAD` only and does not list directories. Each project gets one fixed label. New capability `preview_dir` (follows `preview.enabled`); `preview.open`, `preview.list`, the tunnel hello and the preview launch now carry `port` or `dir`.
- Web UI: links to local files in what the agent writes (messages, thinking, subagent results) and in plan cards open inside anycon. An absolute path, `file://` URL or path relative to the session's working directory that falls inside a project on the node goes to the file browser; an `.html` / `.htm` file opens as a web page in a new tab through a directory preview when the hub has a preview domain and the node supports it. Local images in messages load through the node. Paths outside every project (for example `~/Downloads`) are not links: hovering explains why and clicking copies the path. The file browser has an "Open as web page" button for HTML files.
- Web UI: an empty Inbox shows the logo, which moves once when the list is cleared, and a line about today in place of the explanation, for example "Today: 4 sessions moved forward · 12 requests answered in this browser". The session count comes from the session list already in the browser (sessions on the ticked nodes, not archived, whose last event is from today). The answer count is kept in this browser only, per node, and starts again each day; it counts every answer to a permission request, plan or question, not only approvals. A number that is zero is left out, and with nothing to say the explanation stays.
- Web UI: the Twin page's statistics are redesigned. Today's numbers are cards with an icon, a large figure and a small graphic: wakes get a bar split by result with a legend, dispatches and judgment calls get a usage bar against the daily limit with "N left today" (it turns amber from 80% and red when the limit is used up), and a token-only cost shows input large and output below. The last and next wake moved into one line under the cards, with today's times written as just the time. The trend now leads with a stacked column chart of wakes per day (acted, failed, idle or stopped early), with a readout line for today that switches to the day you hover or pick with the arrow keys; the range summary is split into "What Twin did" and "How it ended", and the day table moved into a collapsed "Day by day" section with right-aligned figures. "Now" shows each group in its own box, and the run history is a divided list with a result dot per run. No chart library is added.
- Web UI: the line at the end of a turn now starts with what the turn did: how long it took and how many files it changed (left out when the turn's start is not among the loaded events, so the number is never too small). A turn that finishes normally while you are watching it gets a check mark that draws once. Two new switches under Settings > Appearance, both off by default: a short chime and, on Android, a vibration when such a turn finishes. Neither fires while the page is hidden. The chime is synthesized in the browser; no audio file is added.
- Claude Code adapter: a "Claude in Chrome" session option (`chrome`, off by default). When on, the session's `claude` process starts with `--chrome`, so the agent can use the Chrome browser on the node's machine through the Claude in Chrome extension, with the accounts signed in there. Without it a headless `claude` has no browser tools. It needs the extension installed and connected, and a Claude Code version that has `--chrome`. Changing it takes effect when the session's process restarts.
- Web UI: the Twin page is now a run-status page, and Twin configuration moved to **node settings > Twin** (`?tab=twin`, only on nodes that support Twin). The page shows, per node: a status head with Pause / Resume / Look now / Dry run (Resume runs a dry run first and shows the plan in a dialog; "Do it this way" is enabled only for a `done` or `idle` result, then unpauses and wakes; when there is no usable plan, for example because today's judgment-call budget is used up or the dry run failed, the dialog explains why and offers "Resume without a dry run", which unpauses and wakes with the current scope and rules; Look now says the wake comes within about a minute because triggers are coalesced); a one-line summary of the configuration; today's wakes (acted / idle / failed, with budget-limited and cancelled wakes counted apart), dispatches, judgment calls, cost, last and next wake; an alert when the last two or more real wakes failed; what Twin is working on, what waits for you (and for how long), what is queued and what it did not get to last time; a 7 / 30 day trend (a summary and a per-day table, numbers only); and the run history, with the cost or token count of each run. A Twin that is not configured shows only its state, what is missing and a "Set up" link. The new tab holds the scope and budget form with the first-time flow (save paused, dry run, plan, "Do it this way"), the judge backends (`judge.*` and `twin.*` settings, moved out of Limits on nodes that support Twin), "Use other nodes", and "Used by other nodes" (the twin devices paired with this node, with the scope dialog). Without the `twin_stats` capability the page falls back to today's counts and the last wake computed from the loaded runs in the browser's day, and hides cost, next wake, queued, not-looked-at and the trend.
- Protocol and daemon: `twin.get` gains `last_run`, `next_wake_ms`, `queued` and `deferred`; `TwinRun` gains `usage` (the sum of its judgment calls' `input_tokens` / `output_tokens` / `cost_usd`, absent when none was reported); new read method `twin.stats { days? }` returns one entry per node-local day (wakes by result, dry runs, judgment calls, usage, executed decisions by action, skipped, handed back, taken over, accepted, dropped, and the turnaround from first dispatch to acceptance) from the run records and item history kept on the node; `node.info.capabilities.twin_stats` says the daemon serves all of this, and older daemons simply lack the fields. The first message of a session the twin dispatches now asks the agent to end with a short report: what changed, how it was verified and what is left.
- Twin connections, the node-being-used side ([ADR-56](docs/decisions.md#adr-56-twin-可以使用别的节点daemon-作为受限设备配对范围由被使用的节点定) step 5, [spec](docs/spec/daemon.md#27-twin-连接)): another node's twin can be paired with this node as a restricted device of the new kind `twin`. A person asks for a one-time code with `node.twin_link_code` / `anycon twin link-code` (16 characters, 10 minutes, one at a time); that code accepts only a twin device, and ordinary pairing codes, join codes and the node password refuse the `twin` kind (`twin_not_allowed`). The node enforces what a twin device can do: a fixed method whitelist (`node.info`, `agent.list`, `twin.peer_status`, and the to-do and session methods only for the items it added and the sessions it dispatched; everything else, including other people's items and sessions, is `forbidden` with `data.reason = "twin_device"`, before `not_found`), and only the `todo.changed` / `todo.event` / `session.changed` / `session.event` of its own items and sessions are pushed to it (no other notification, no `notify`). Its scope (projects, sessions at once, dispatches per day, agent, model, mode, pause) is stored per connection on this node, defaults to nothing open, and is read and changed with `twin.get` / `twin.set { requester }` or `anycon twin status|set --requester <device>`; dispatches from it always use a worktree with "no push, no pull request". `[twin] accept_links` (default `true`, hot-reloaded, remote changes can only tighten it) disconnects existing twin devices and refuses new ones while keeping their records and scopes; `node.info.twin_accept_links` reports it. Making and revoking a twin connection sends `node.security_event` (`twin_linked` / `twin_unlinked`) and a `security` push to the other devices and is audited. Protocol: `DeviceKind` `twin` and `unknown`, `node.twin_link_code`, `twin.peer_status`, `twin.link` / `twin.links` / `twin.unlink` (the using node's side, below), `Todo.remote`, the `remote_dispatched` / `remote_result` history events, `TwinDecision.node`, the skip reasons `remote_unavailable` / `remote_refused`, `EnrollRejectReason` `twin_not_allowed` and `unknown`, security event kinds `twin_linked` / `twin_unlinked`. The hub accepts the `twin` kind like any other device (no migration; it refuses device kinds it does not know at sign-in). A twin device can have at most 100 open items on a node (`todo.add` then fails with `invalid`, reason `too_many_twin`); people's own items are not counted. Downgrading a node does not turn a twin device into an ordinary one: the older daemon refuses to start on a database with migrations it does not know (sqlx `VersionMissing`), so a twin link cannot fail open; restoring an old backup only brings back the peers it had.
- Twin connections, the using node's side ([ADR-56](docs/decisions.md#adr-56-twin-可以使用别的节点daemon-作为受限设备配对范围由被使用的节点定) step 5, [spec](docs/spec/daemon.md#27-twin-连接)): a node's twin can now use other nodes on the same hub. `twin.link { code, node_id }` (`anycon twin link <code> --peer <node id>`) pairs this node's daemon, as a device of kind `twin`, with the node that issued the code and fails, forgetting the pairing, if the code belongs to another node; `twin.links` (`anycon twin links`) lists the links with their online state and the node's last `twin.peer_status`; `twin.unlink` (`anycon twin unlink <node>`) forgets a link on this node only, the twin device stays paired on the other node until you revoke it there. All three are for people only (a `twin` device or a connection that declared `mcp` gets `forbidden`), and `link` / `unlink` are refused inside an anycon agent session. The twin device has its own keys in `<data dir>/twin/` (the same files as the CLI's device identity, created on the first link and read only by the daemon), connects to this node's own hub only, and the daemon keeps one long connection for all links while at least one exists, whether or not `[twin] enabled` is on. Each wake sends the twin a table of the linked nodes (name, group, online, open projects, agents, free sessions and dispatches, at most 4 KiB, wrapped in the same random boundary as the items); a `dispatch` decision may name a `node` and a `project` on it, and the daemon then adds the to-do on that node and dispatches it there. The to-do here records the remote item (`Todo.remote`, `remote_dispatched`), the session's results come back into its history as `remote_result` (fetched from the other node's history, so a restart or a reconnect fills in what was missed without repeating anything) and wake the twin, and the remote item's activity counts toward the to-do's `activity`. A node that is offline or refuses (`remote_unavailable` / `remote_refused`) counts as a failed dispatch, three in a row hand the item back, and dispatches to other nodes count toward this node's daily limit. There is no proxy: nothing on this node can call another node through it. Protocol: `TodoDispatchParams.note` (the twin's note for the first message; only a twin device can send it). When the hub rate-limits WebSocket upgrades (HTTP 429), `twin.link` waits for the hub's `Retry-After` (2 seconds and doubling if there is none, 30 seconds in total) and tries again, and fails with `busy` and `data.reason = "hub_rate_limited"` if the hub keeps limiting; the long connection's reconnect and `anycon connect` follow the same `Retry-After`. Database: forward migration `0013_twin_links.sql` (`twin_links`, `todo_remotes`).
- Twin connections, the using node's clients ([ADR-56](docs/decisions.md#adr-56-twin-可以使用别的节点daemon-作为受限设备配对范围由被使用的节点定) step 5, [spec](docs/spec/daemon.md#276-客户端)): node settings > Twin has a "Use other nodes" section that lists the connections (node, online, open projects, sessions and dispatches left) and adds one by asking the other node for a code (`node.twin_link_code`) and handing it to this node (`twin.link`); the code only passes through memory and is never shown, logged or stored. Only paired nodes that support Twin, accept links and are online can be picked (the rest are greyed out with the reason); nodes in different groups need a second confirmation; failures are explained by reason. "Disconnect" (`twin.unlink`) says the twin device must still be revoked on the other node. On the node being used, a twin device in Settings > Devices has a "Scope" button (`twin.get` / `twin.set` with `requester`, nothing open by default). History shows `remote_dispatched` / `remote_result` (with a link to the other node when this device is paired with it), twin decisions show the node they went to and the skip reasons `remote_unavailable` / `remote_refused`, and `twin_linked` / `twin_unlinked` security events have texts. TypeScript SDK: `node.twinLinkCode()`, `node.twin.link` / `links` / `unlink` / `peerStatus`, and `requester` on `node.twin.get` / `set`.
- Twin connections, takeover and stuck sessions ([spec](docs/spec/daemon.md#27-twin-连接)): when you send a message in a session another node's twin dispatched, the node you are on records a `taken_over` in the item's history (once per session) and pushes it to that twin device; the twin's node picks it up on the next sync of the remote item (the same path that fetches results, so a restart or a missed notification does not lose or repeat it) and treats it like a local takeover: the handler goes back to you, the history gets a `taken_over` with the new optional `node_id`, its open question is voided, and results of that turn no longer wake the twin. The history shows "You took over on <node>". A remote session that is running but whose `last_seq` has not changed for two hours (counted on the twin node's own clock, restarted by a restart, by the other node reconnecting and by a new dispatch; an unreachable node is not judged) now hands the item back too, with the node named in the reason. Protocol: `TodoEventData::TakenOver.node_id`.
- Web UI: **Settings > Storage** (`/settings/data`). It shows how much this site stores in the browser and the browser's limit, the size of the session history and attachment caches, and a "Clear the cache" button that frees space without signing out or pairing again: it removes the cached session history and attachments, but keeps the attachments that drafts and unsent messages still need, and leaves the device key, paired nodes, drafts, unsent messages, the session list and the to-do list alone. Opening a session loads its history from the node again. The page also asks the browser to keep the site's data when space runs low (persistent storage), and explains what happens when it says no. The "could not save data locally" banner now has a "Manage storage" button that opens the page.
- Web UI: the session history cache is now capped. It keeps the 20 sessions opened most recently in this browser, up to their newest 2,000 events each; sessions open in the tab are never touched, and anything older is loaded from the node when you open it or scroll up. Sessions cached before this version count as the oldest, so most of an existing cache goes on the first prune. The local database moves to version 4 (a new `event_meta` store); as with earlier upgrades, other tabs still running the previous version are sent to the sign-in page when a tab on the new version opens the database.
- Add the node's twin (4a): scoped, budgeted triage, worktree dispatch with no push, questions and advisor calls, hand-back and takeover, run history, dry runs (also while the twin is paused), pause/resume and `anycon twin`; `anycon todo add --twin` and `todo assign` choose the handler. Triage sends assigned items and their earlier results to the configured judgement backend: an `api` backend receives them directly from the daemon over HTTPS, outside the hub, while an `agent` backend sends them through the local agent CLI to its model provider. The twin cannot approve permissions.
- Repeating to-dos ([spec](docs/spec/daemon.md#269-周期项和-pr-事件4b)): a to-do with a `repeat` rule (`daily`, `weekdays` or `weekly` on a weekday, at an `HH:MM` on the node's clock) is a template that the node copies into a new open item at each time, skipping a time while the previous copy is still open and never queueing up what was missed while the daemon was down (only the latest time, if it was less than a day ago, is made up). A template is never triaged by the twin and cannot be dispatched; only a person can set a rule. `anycon todo add --repeat daily@09:00` / `weekdays@09:00` / `weekly:mon@09:00`, `anycon todo edit <id> --repeat <spec> | --no-repeat`, a REPEAT column in `anycon todo ls`, `repeat` in the SDK's `todos.add` / `update`, and a "Repeat" control, a "Repeating" group and a "From a repeating item" chip in the Web UI (shown only when the node reports `capabilities.todo_repeat`). Protocol: `TodoRepeat`, `TodoSourceKind` `repeat` with `TodoSource.todo_id`, `repeat_created` / `repeat_skipped` history events, `ClearableTodoField` `repeat`; the daemon database gets the forward migration `0010_todo_repeat.sql`.
- Repeating to-dos, several times a day ([spec](docs/spec/daemon.md#269-周期项和-pr-事件4b)): a rule can be `interval`, for example weekdays every 2 hours from 09:00 to 18:00 (`days`, `every_min` of 15 to 720, `until`; the times follow the node's clock and its daylight-saving rules). CLI: `--repeat weekdays@09:00-18:00/2h` (or `weekly:mon@09:00-12:00/30m`); Web UI: an "every" choice and an end time next to the repeat time. It is a new rule kind, so older clients show it as a rule they cannot read instead of a wrong single time. Needs `capabilities.todo_repeat_interval`.
- Repeating to-dos, auto-close: a template can be set to close its copies when the twin decides they are done (`repeat.auto_close`; CLI `--auto-close` / `--no-auto-close`, a checkbox in the Web UI), so a patrol-style to-do is not skipped forever while each copy waits for review. This is an exception to "only people set a to-do's state": it only applies to copies of a template that a person switched it on for, only on the twin's `done`, and the history says the repeating item closed it.
- Repeating to-dos, run once now: new request `todo.repeat_now { id }`, `anycon todo repeat-now <id>` and a "Run once now" button copy a template right away without changing its schedule. It is refused for a template that is closed or not yet reviewed, while its previous copy is still open, and for agents. The history entry `repeat_created` gets `manual`; `RpcErrorData` gets `todo_id` (the open copy for `previous_open`). The daemon database gets a forward migration (`0017_todo_repeat_interval.sql`).
- Repeating to-dos, state across runs ([ADR-65](docs/decisions.md#adr-65-周期项的跨次状态模板上一张键值表agent-经-cli-读写), [spec](docs/spec/daemon.md#2611-周期项的跨次状态)): a template can keep a small key → value table that the agents in the sessions of its copies read and write, so a patrol-style to-do ("check the open merge requests every two hours") can skip what an earlier run already handled instead of leaving a marker in the outside system. A person switches it on per template (`repeat.keep_state`; CLI `--keep-state` / `--no-keep-state`, a checkbox in the Web UI); it is off by default. The agent uses `anycon todo state unseen | set | get | ls | rm --todo <id>`; `clear` is left to people. Keys (up to 200 bytes) and values (up to 1 KiB) are opaque to the daemon, a template holds up to 2,000 entries and drops the ones written longest ago when full. This is the one place an agent may write to the to-do list: titles, notes, state, handler, repeat rules, deletion and dispatch stay closed to it. The entries are user content: they are stored in plain text in the daemon's database, never in logs or the audit log (which records lengths and counts), and the Web UI does not cache them. Reading or writing state does not change the item's `updated_ms`. Each run's history gets a `state_usage` entry with its read and write counts. State does not follow an item dispatched to another node over a twin connection. Needs `capabilities.todo_repeat_state`; the daemon database gets a forward migration (`0019_todo_repeat_state.sql`).
- What anycon adds to a dispatched task is now shown before it is sent. With state switched on, the first message gets a short usage note, and the checkbox shows that exact text; "Include usage notes" (`repeat.state_hint_off`) leaves it out, with a button to copy it into the notes and edit it there. A template's page has "Preview what the agent receives" (new request `todo.repeat_preview`, which also reflects unsaved form fields), and both it and the dispatch dialog's preview label each part as written by you or added by anycon (`segments` on `todo.dispatch_preview`): earlier reports, the state usage note, the closing-report request and the no-push line. The hint under the notes field no longer says the title and notes are the whole task description. An "Insert an example" menu puts a sample key convention (merge requests, Jira, a cursor) into the notes.
- Twin: pull requests of the sessions it dispatched are watched by the existing `gh pr view` poll, whether or not `worktree.auto_archive_on_pr_close` is on (it only archives when on). A failing check, a merge, a close or new review activity adds a `pr_event` entry to the to-do's history and wakes the twin (trigger `pr`, new in the protocol); no push notification. The twin's triage input gets one `pr:` line per item with the PR number, state, check summary, review count and latest review time, and never any review or comment body, because anyone can comment on a public repository. New forward migration `0011_twin_pr.sql`.
- Stale rules and "Always do this" (twin 4c): a rule that is active but has not been injected into a session, cited by a twin decision, or switched on again for 60 days is marked `stale` by the daemon once a day. A stale rule is no longer given to agents and does not count toward the 4 KiB rules limit, but it is never deleted; only a person restores it (`rule.update { stale: false }`, the same size check as switching a rule on; `anycon rule restore <id>`; the Rules page has a collapsed "Stale" section with a Restore button). `rule.changed` is sent when a rule is marked or restored, and the audit log records the automatic mark as `rule.update` with `auto: "stale"`. When you answer an agent's question or one of the twin's questions, an "Always do this" box opens the same "Record as a rule" editor after the answer succeeds; the prefilled text cannot be saved unchanged and nothing is saved in one click. The box does not change the answer, the answer buttons' lock or Cmd+Shift+A / D. Protocol: `Rule` gets `last_referenced_ms` and `stale`, `rule.update` gets `stale` (only `false` is accepted); migration `0012_rule_stale.sql`. The twin's triage prompt now lists the ids of the rules it is given so a decision can cite them.
- Follow up marker ([ADR-53](docs/decisions.md#adr-53-会话标注待处理是布尔标记未读是已读水位都和归档分开)): flag a session to be reminded when its turn finishes, or to come back to it later. Flag it from the session header, the "Remind me when done" button next to the input, a session row, or the command palette. A flagged session that has stopped is listed in the Inbox (the one waiting longest first), counts in the tab title and app badge, and pops a toast when you are on the page; when you are away the node sends a new `follow_up` push notification, which you can switch on or off under Settings > Notifications. Opening the session or replying does not clear the flag, only "Mark done" does. The project page has a "Follow up" filter.
- Unread dot: a session that has stopped with output you have not seen shows a red dot and a bold title in the session list and the sidebar. The node keeps a read position per session (`session.mark_read`), shared by all your devices.
- Protocol and daemon: `SessionSummary` and `session.changed` carry `follow_up` and `read_seq`; new requests `session.set_marks` and `session.mark_read`; new notification category `follow_up`. The daemon database gets a forward migration (`0003_session_marks.sql`). The web UI needs a daemon with these requests, so upgrade both together.
- Web UI: **Inbox** (zh: 待处理) is the new home page (`/inbox`; `/` redirects there when the browser has paired nodes). One list, across the nodes ticked in the node filter, of everything that waits for you: permission requests, plans and questions, device requests, sessions flagged for follow-up that have stopped, and sessions that failed in the last 7 days. Permission requests use the same card as the session page, with the full command, working directory, node and session, and there is no way to answer one without its details on screen: on desktop the selected row's details sit in the right half, on tablets they slide in from the right, on phones the first item is expanded. Nothing can be approved from a row, a notification or a swipe. After you handle an item here focus moves to the next one; an item that was handled somewhere else leaves a "Handled elsewhere" placeholder instead of selecting another request for you, and a newly shown request keeps its buttons and shortcuts locked for a moment. Data from an offline node is marked as cached. Running sessions, including ones flagged "Remind me when done", sit in a collapsed "In progress" row below.
- Web UI: on phones (< 768px) the left drawer holds the same sidebar as on desktop, with Inbox and To-dos (with their counts), Twin and Rules on top ([ADR-58](docs/decisions.md#adr-58-手机上的主导航回到左侧抽屉)). Every page's top bar has the menu button; pages you reach from another page (an item, a review, node settings, a new session, files) also get a back button that follows browser history. The Inbox and the to-do list stay mounted while you visit other pages, so they keep their scroll position, unsent input and "Handled elsewhere" placeholders. `/sessions` and `/more` redirect to the Inbox.
- Web UI: keyboard `G` then `I` / `S` (go to Inbox / back to the last session), `J` / `K` and `Enter` in the Inbox, and Cmd+Shift+A / D on the selected request there. Single-letter keys do nothing while you type or a dialog is open. Changes of the Inbox count are read out by a screen-reader live region.
- Web UI: people who upgrade see a one-time notice that the home page changed and where the node home went.

- Web UI: **spaces.** Nodes whose group name (Settings > Limits > Group, or "Manage spaces…") is the same form a space. When any node has a group, the node filter becomes a space switcher: choose All, a space or hand-pick nodes; the Inbox, the to-do list, the session tree and the command palette search follow it, the count and badge only count the current space, and the dot on the switcher says how many things wait in which other space. On phones the top bar of the Inbox, the to-do list and the Twin page shows the current space. Content opened from a notification outside the current space is shown with a note and a "Switch to this space" button, never switching by itself. "Manage spaces…" sets a node's group and renames a space on every online node (offline ones are listed as not changed). The default node of "add a to-do" is remembered per space, and notifications show the space name next to the node name. With no groups nothing changes: it is the same node filter, and stored choices keep working.
- Web UI: **move a to-do to another node** ("Move to another node…" on the item and in the row menu). The node, not this tab's cache, is asked before anything destructive: the source is read first and must be unchanged, the copy on the target is read before the source is deleted, and the source is deleted only if its `updated_ms` is still the one you confirmed. If anything fails the item stays on the source, and the message says what exists where. "Delete the copy on …" removes a leftover copy only while the source is still there and the copy has not been edited. Both nodes must be online and finished syncing, the item must have no unsent changes, and an unreviewed agent item cannot be moved; moving into another space asks first. Two narrow windows remain, because there is no transaction across two nodes: a copy deleted on another device in the round trip before the source is deleted, and the source deleted on another device in the round trip before the copy is deleted; in both cases neither node ends up with the to-do. Every message says whether a copy exists, may exist or does not, retrying a state restore never overwrites a change made to the copy elsewhere, and closing the page while a move runs asks first.
- Daemon and protocol: new request `todo.get { id }` (read one to-do; no audit, no notification) and an optional `if_updated_ms` on `todo.delete` (refused with `invalid`, reason `changed` and the current `updated_ms` in the error data when the item changed). `updated_ms` is now strictly increasing per item (`max(now, old + 1)`), so a write in the same millisecond or after a clock step back can no longer leave it unchanged. The TypeScript SDK has `node.todos.get(id)` and `delete(id, { ifUpdatedMs })`.

The first message quotes every line of each earlier report with `> `, normalises every kind of line break first, and ends the block with an explicit line.

It is worked out from the linked sessions each time the item is returned: waiting for a permission, or no session left, is `waiting`; running, queued, background tasks still running or a turn result not yet recorded is `working`; otherwise the latest session decides (`review` after a normal turn whose result is in the item's history; an error, an interruption by a restart, a cancelled turn or a result that never got recorded is `waiting`). A closed item has none. Session activity never changes `updated_ms`, so conditional deletes keep working while a session runs. `todo.changed` is sent when it changes. Deleting an item deletes its links and history; deleting a session keeps the link; closed items take their history with them when `sessions.history_retention` removes them.

After approving, "commit, push and open a pull request" asks for an explicit confirmation before it turns "no push" off for that session.
  - Web UI: a session that came from a to-do shows a chip with the item's title and lists the item in its info panel; the sidebar folds those sessions into one "From the to-do list" row per project (switchable in the appearance settings); the finished-turn notification reads "<title> is ready to review" and opens the review page (not for an item that is already closed); permission requests of such a session name the item; the Inbox "In progress" also lists the items an agent is working on.

- Daemon: **update check** ([ADR-57](docs/decisions.md#adr-57-daemon-每天向-anyconai-检查一次新版本只提示不下载), [spec](docs/spec/daemon.md#24-更新检查)). A few minutes after it starts and then about once every 24 hours, the daemon asks `https://anycon.ai/releases.json` whether a newer release exists. When one does, `node.info` carries `update_available { latest, url, checked_at_ms }`, the Web UI shows it under node settings > About with a link to the GitHub release page, `anycon doctor` has a new `update` line, and the daemon logs one info line. - Decision profile, first half ([ADR-54](docs/decisions.md#adr-54-清单决策档案和-twin都在-daemon-上twin-不能批准权限), [spec](docs/spec/daemon.md#23-决策档案)): rules, short instructions such as "write the failing test first", kept on each node. The active ones are written into the system prompt (`system_prompt_append`) of every session that `todo.dispatch` opens; manual sessions get them only when you set `rules.inject_manual_sessions = true` (off by default, hot-reloaded, editable from a paired device). Rules never change permissions. There is no model call, and no automatic extraction or sync between nodes yet.
  - Rules are at most 600 characters (line breaks allowed) and 300 in all. A session gets at most 4096 bytes of rules, template included, measured in bytes (Chinese text takes more). The limit is checked when a rule becomes active or an active rule's text or project changes; a change that would go over is refused with `over_budget`, nothing is cut and nothing is picked for you.
  - Limits that keep agents from crowding you out: at most 50 agent-proposed rules can wait for review (`too_many_pending`, only for the agent path; your own rules are not affected); rejected rules do not count toward the 300 and have a cap of 300 of their own, and when it is full the oldest rejected rule is deleted (the only automatic deletion; pending, active and disabled rules are never touched). A rule cannot contain bidirectional controls or zero-width characters, so what is injected can be reviewed.
  - `anycon rule show <id>` prints a rule in full (text, status, project, source); `confirm` and `enable` print the full text of the rule they activate. An agent-proposed rule records the session it came from (`origin_session` on `rule.add`, `ANYCON_SESSION_ID` in the CLI). `todo.dispatch_preview` takes an optional `project`, so `rules_text` matches a dispatch to another project.
  - A rule you write is active at once. A rule an agent proposes is `pending` until you confirm it: `rule.add` with `agent: true`, or from a connection that declared itself `mcp`, is forced to `pending` with source `agent`, and such a connection cannot update or delete rules. Rules are never deleted automatically and are not affected by `history_retention`; `anycon export` does not include them. The text of a rule stays out of logs and the audit log.
  - Agents that cannot take a system prompt (ACP agents) get no rules; the dispatch still works and its history records `rules_skipped: "unsupported"`. `AgentInfo.capabilities.system_prompt` says which agents can.
  - Protocol: `rule.list`, `rule.add` (idempotent on `id`), `rule.update` and `rule.delete` (both take `if_updated_ms`), `rule.preview`, the `rule.changed` notification, `node.info.capabilities.rules`; the `dispatched` history event carries `rules` (the ids injected); `todo.dispatch_preview` returns `rules_text`; error data can carry `bytes` and `cap`. The daemon database gets a forward migration (`0006_rules.sql`). `rules.inject_manual_sessions` is a new remotely editable setting.
  - CLI: `anycon rule add <text> [--project]`, `anycon rule ls [--all] [--json]`, `anycon rule confirm | reject | disable | enable <id>` and `anycon rule rm <id>`. Inside an agent that anycon started, `anycon rule add` proposes a pending rule and the others refuse. `anycon todo run --dry-run` also lists the rules text and `anycon todo history` shows how many rules each dispatch used. TypeScript SDK: `node.rules.*` and the `rule_changed` event. `anycon mcp` has no tool for rules.
  - Privacy: an active rule is an instruction in the system prompt of every dispatched session. Anything not written by a person waits for your confirmation, but the "written by an agent" marker is self-reported, so it is a guard rail and not a boundary (see `SECURITY.md` and `docs/architecture.md` § 5.6).
  - Web UI: **Rules** (zh: 规则; `/rules`, in the sidebar, under More on phones and in the command palette, only when a node supports rules). Two tabs, To review and Active, with disabled and rejected rules folded under Active. Every rule shows its whole text as plain text, its scope (all projects or one project), where it came from (written by you, recorded from an answer, proposed by an agent with a link to that session, extracted) and when a session last used it. Add, edit, edit then confirm, confirm, reject, disable, enable and delete (after a confirmation); select several waiting rules to confirm or reject them together. "Used / limit" is shown for the sessions of every project, and a refusal for going over the limit says how many bytes the rules would take and what to do. A change is sent with the version you were looking at, so a rule edited on another device is never overwritten: you are told, and shown the new version. Rules are kept in memory only and need the node to be online to change.
  - Web UI: rules proposed by an agent wait in the Inbox "Later" section, one row per rule. The row has no buttons: open it to read the whole rule, then confirm, edit then confirm, or reject. They are never selected or expanded on their own, are not counted in the Inbox number, the badge or the tab title, and are not pushed.
  - Web UI: **Record as a rule** next to the answer buttons of a permission request or a question, on the session page and in the Inbox. It opens an editor prefilled with the question and your choice, with what the agent wrote shown apart from your choice; you edit the text and save, and the rule is active with that answer as its source. It does not answer the request and does not touch the answer buttons or their shortcuts.
  - Web UI: the to-do dispatch dialog shows the rules that will be added to the new session's system prompt (asked again when you change the project), or says that the chosen agent does not receive rules; a session's info panel shows the rules it was given, read-only.
  - Web UI: the node setting `rules.inject_manual_sessions` is under Settings > Limits.

- Decision profile, second half: **rule extraction and the judgement backend** ([ADR-54](docs/decisions.md#adr-54-清单决策档案和-twin都在-daemon-上twin-不能批准权限) step 3, [spec](docs/spec/daemon.md#239-提炼), [judgement backend](docs/spec/daemon.md#25-判断后端)). The node can turn decisions you made in a session into rules for you to review.
  - Decision points are picked by the daemon, not by a model: an answered permission request or plan that carries your words (a deny reason, plan feedback), an answered question, a message you sent while a turn was running, and the first message after you cancelled a turn. An extraction sends at most 40 of them (24 KiB of excerpts, what you said kept apart from the agent's text around it) and the text of your existing rules (at most 8 KiB) to the backend.
  - Every proposed rule is checked like a rule you add and dropped if it repeats an existing rule (rejected ones included) after normalising case, width and spacing. At most five per extraction; they are always `pending` and show where they came from (the session and the event). A per-session watermark means a decision point is extracted once.
  - When it runs: on request ("Extract rules" in the session page's More menu, `anycon rule extract <session>`), or with `rules.extract_auto = true` (off by default) for sessions idle for 30 minutes, at most 7 days old. A failed automatic extraction is retried after a day, at most three times. One extraction runs at a time.
  - Judgement backend, configured only in `config.toml` (`[judge]`, `[judge.backends.<name>]`): `kind = "api"` calls the Anthropic Messages API or an OpenAI Chat Completions compatible endpoint (HTTPS, or plain HTTP on loopback; key from `api_key_env` or `api_key`), `kind = "agent"` runs a one-shot call of Claude Code (no tools, no MCP servers, no saved session; 2.1.325 or newer) or Codex (`codex exec` in an ephemeral read-only sandbox; 0.169.0 or newer) in an empty temporary directory. `judge.daily_calls` (default 20, failures count) caps calls per local day. Paired devices can pick among configured backends, change the daily limit and toggle automatic extraction; they cannot set up a backend.
  - Protocol: `rule.extract`, `rule.extract_runs`, the `rule.extract_done` notification, `node.info.judge`, `capabilities.rule_extract`, `AgentCapabilities.oneshot`; budget errors carry `used` and `limit`. CLI: `anycon rule extract [--no-wait] [--json]`, `anycon rule runs`, and a `judge` item in `anycon doctor`. SDK: `node.rules.extract`, `node.rules.extractRuns`, `rule_extract_done`.
  - Web UI: the rules page has an extraction history per node with today's calls; extracted rules link back to the event they came from; node settings list the new keys under Limits.
  - Privacy: with a backend configured, the daemon sends session excerpts to it. An `api` backend is a request the daemon itself makes to that model service, not through the hub; an `agent` backend hands them to that agent's CLI and its provider, and Codex can still run read-only commands there. Prompts and replies are not stored or logged; each call records only sizes and token usage. Nothing is sent when no backend is configured.
- Decision profile, group sync ([spec](docs/spec/daemon.md#238-同组节点之间的同步)): Web copies group rules to every other paired node in the same nonempty group after a successful user write. IndexedDB keeps the latest desired state per target and rule, replays after reconnect, and keeps refusals for manual retry or discard. Rules show group scope and pending or failed sync; “Align group nodes” compares text, status, scope and missing copies, treating offline nodes as unknown, and lets you choose a version or delete all copies. Add, edit and confirmation offer a scope selector; project and pending rules cannot sync. Switching back to node scope leaves other copies intact. CLI `rule add --group` marks a rule on one node and explains Web sync; `ls` / `show` display scope. SDK add / update accept `sync` and do not write across nodes.

### Changed

- The agent start timeout is now set per agent and defaults to 2 minutes instead of a fixed 60 seconds ([ADR-64](docs/decisions.md#adr-64-agent-启动超时按-agent-配置缺省-2-分钟), [spec](docs/spec/daemon.md#71-状态)). It covers the time from sending a message to the agent's first output, which for Claude Code includes the model reading the whole conversation, so a long conversation could time out on every message while a new session with the same agent worked. Set it with `agents.<id>.start_timeout` (`agents.acp.<id>.start_timeout` for ACP agents; 10s to 1h, hot-reloaded, applies to turns already starting). The remote config whitelist now has per-agent keys: `node.get_config` lists `agents.<id>.start_timeout` once for every agent in the config, with the value in effect (`2m` when the file doesn't set it), and `node.set_config` changes it with the same checks and `config.changed` audit as the other keys; no protocol change. The other `agents.*` keys (`command`, `env`, `enabled`, `default_*`) still can't be changed remotely. In the Web UI each agent card under node settings > Agents has an "Agent settings" block, saved apart from the new-session defaults; Limits no longer shows `agents.*` keys, and older daemons list none, so the block is hidden. The `agent_start_timeout` error message now names the actual wait, for example `agent did not respond within 2 minutes`.
- The Chinese Web UI and docs call the node's twin **Twin** too, instead of 分身 ([ADR-63](docs/decisions.md#adr-63-界面文字从-bot-改回-twin中文也写-twin)). Nothing you type changes: the protocol methods (`twin.*`), the `[twin]` config section, `anycon twin`, `--twin`, the `/twin` route and the device kind `twin` keep their names.
- Web UI: Twin and Rules no longer take two rows in the sidebar ([ADR-61](docs/decisions.md#adr-61-twin-和规则合成一个入口放在左栏底部待处理和清单放到节点过滤下面)). The Twin status at the bottom of the sidebar is now the one way in: its first line says Twin, its second line what the twin is doing on the ticked nodes, and it opens the Twin page, whose top bar has two tabs, **Twin** and **Rules**. With no node supporting the twin, that row says Rules and opens the Rules page. `/twin`, `/rules` and their links keep working. Inbox and To-dos moved below the node switcher, since both count only the nodes ticked there.
- Web UI: on phones (< 768px) messages no longer have the "…" button with "Add to to-dos": without hover it was always shown and covered the message text. Select text in a message to add it to the to-dos instead; tablets and desktops keep the button.
- Follow up marker ([ADR-59](docs/decisions.md#adr-59-follow_up-是只提醒一次的完成后提醒由-daemon-消费不是待处理书签)): the flag now means "notify me when this is done" and fires once. When the session really finishes (after its background tasks end, as before) the daemon sends the `follow_up` notification and clears the flag in the same step; the session is then an ordinary one with the unread dot. A flagged session no longer shows up in the Inbox, and "Mark done" is gone. Flagging a stopped session means "notify me when the next turn finishes", not "come back to this later". A failed turn clears the flag (errors have their own notification and an Inbox entry); cancelling a turn keeps it. The input bar says "You will be notified when this session finishes" while the session or its background tasks run, "...when the next turn finishes" otherwise; it no longer claims a session is waiting for you while background tasks still run. The project page filter is "Notify when done (n)" and lists every flagged session. The foreground toast now appears only when the daemon reports it consumed the flag, so cancelling the reminder on another device no longer produces a "finished" toast. Protocol: `session.changed` has a new optional `follow_up_fired` (true only for the change that consumed the flag). The daemon database gets a forward migration (`0015_follow_up_once.sql`) that clears `follow_up` on every session that is not running, starting, queued or waiting for approval, since those were "follow up" bookmarks under the old meaning; imported sessions never carry the flag. An old daemon does not clear the flag, so upgrade the web UI and the daemon together.
- Upgrading to 0.4: **back up before you upgrade**: the hub's data (the SQLite file, or the Postgres database) and each node's daemon data directory (`~/.anycon/`). This release adds database migrations on both the hub and the daemon, and migrations only move forward. An older version refuses to start on data a newer one has migrated (the daemon prints `error: error: store: migration: migration 3 was previously applied but is missing in the resolved migrations`, the hub `migration error: migration 5 was previously applied but is missing in the resolved migrations`), so rolling back means restoring the backup, and anything added after the upgrade is lost. **Twin connections and twin questions pushed to your clients need a 0.4 hub as well**: a 0.3.x hub rejects twin devices (`twin.link` fails with `hub_unsupported`) and does not push twin questions, though clients that are online still receive them. Upgrade the hub first, then the nodes. From 0.4 on, starting on data written by a newer version fails with a message that says so and what to do. When a start applies new migrations, the hub and the daemon log the version they migrated from and to.
- CLI: an error that has no specific code is printed as `error: <message>` instead of `error: error: <message>`.
- Hub: a device that stays connected has its last-seen time refreshed every 10 minutes (previously only when it connected and disconnected), so a "last seen within 15 minutes" filter roughly means "online now". With it the hub now stores the network prefix of the IP address each device last connected from (`devices.last_ip_prefix`: IPv4 /24, IPv6 /48, the same format as browser sessions and the audit log; never the full address). Only the latest value is kept. It is not returned by any API and not logged; it stays with the device record (revoked devices keep the value they had) and is deleted with the account. Database: migration `0005_device_ip_prefix.sql`.

- Web UI: the sidebar's pinned "Needs approval" and "Follow up" groups are gone; both are in the Inbox, and the sidebar has an Inbox item with the count above the session tree. The collapsed sidebar rail shows that one count instead of two. The node home page (projects, temporary sessions) moved to "Node home" in the node menu at the top of the sidebar and to More > Nodes on phones.
- Web UI: the app badge, the tab title prefix and the Inbox count are now the same number: approvals, plans, questions, device requests, stopped follow-up sessions and failed sessions (previously approvals and follow-up sessions only), counted for the nodes ticked in the node filter (the old badge counted every node; a dot on the node filter button now shows when other nodes have items waiting). Sessions whose summary says they wait for approval but whose request has not arrived yet are listed as "Waiting for approval (cached)". Clicking a permission-request push notification or toast opens the Inbox on that session's oldest pending request instead of the session page; the push carries no request id, so with several requests in one session it may not be the one that triggered it. Other notification categories open where they did.
- Web UI: the session info panel lists the agent options that are not at their default in the Session card, so a session started with an advisor shows "Advisor model" and the chosen model there. The panel only shows them; they are still changed under "More" below the input.
- Claude Code adapter: the "Advisor model" option has a shorter description.

### Fixed

- Web UI: selecting a to-do (clicking it or moving to it with `J` / `K`) no longer adds an arrow in front of its title, which pushed the text aside and made the row jump. The selected card now has a tinted background and an accent border instead.
- Web UI: a long session title no longer squeezes the node and project names in the top bar's breadcrumb down to a letter or two. The title is what gets cut off; each earlier level is shown in full up to 30% of the breadcrumb's width.
- Web UI: a Markdown link to a local path in a session (such as `[report](/Users/me/report.html)`) no longer opens that path on the hub's address, which never worked and sent the path to the hub.
- Web UI: pairing with a code and unlocking with a node password no longer leave 64 MiB behind in the tab. The Argon2id key derivation they need ran in the page's own crypto module, whose memory never shrinks, so the tab kept it until it was reloaded. It now runs in a short-lived worker that is closed as soon as the key is ready, and the page no longer freezes while it runs. If the worker cannot start, the key is derived on the page as before.
- Web UI: a node could stay disconnected until the page was reloaded when it came back online in the middle of a handshake, or when its key did not match. The finished handshake was freed a second time, the crypto module threw `null pointer passed to rust`, and every later attempt to reset the link threw the same error.
- Web UI: a tab that stays connected for days no longer builds up memory in its resend buffer. Sent messages were kept until the 16 MiB resend window was full, and each one held at least 2 KiB even when it was a few hundred bytes, so the buffer alone could reach over 100 MB. Messages are now stored at their real size and released a minute after they were sent (unless the hub returned them and they wait to be resent). `@anycon/sdk` stores them at their real size too. The connection timing marks in the browser's performance timeline are also cleared from time to time instead of piling up.
- Hub: keep peer offline and online notifications in order when a device disconnects and immediately reconnects, preventing clients from discarding the new session.
- Daemon: changing enrollment settings through RPC no longer produces duplicate audit entries and security events when configuration monitoring runs at the same time.
- `@anycon/sdk`: after a reconnect, a session's `send()` / `events()` stream could miss events. When the SDK reconnected (a hub connection drop, the node going offline and back), it re-watched each session and fetched the history after the last seq it had seen. If a live event of that session arrived while the history request was still in flight, the SDK counted it as seen and then discarded the older history events as duplicates, so those seqs were never delivered; this happened when the session was producing events during the reconnect. Live events are now held until the history has been delivered and then follow it in seq order, so every seq arrives once and in order. If the fetch does not finish because the connection dropped again (the usual cause), the held live events are discarded and the next reconnect fetches the history from the last delivered seq, so they come back with everything missed in between, once and in order. If the connection is still up and the fetch fails for another reason, the held live events are still delivered in order and the events that could not be fetched leave a gap that `session.history({ afterSeq })` fills.

## [0.3.0] - 2026-11-11

### Added

- `anycon mcp` ([ADR-49](docs/decisions.md#adr-49-anycon-mcpstdio-mcp-server-是又一个客户端入口不暴露审批不做编排)): an MCP server on stdio, so another agent can look at and drive the sessions on your node. Nine tools map onto existing RPC methods: `list_agents`, `list_projects`, `list_sessions`, `read_session`, `search_sessions`, `create_session`, `send_message` (waits for the turn by default and returns the final text, status and usage), `cancel_turn`, and `get_diff`. It uses the CLI's connection options, so `--hub` / `--node` / `--local` work as for other commands. There is no tool to approve or deny a permission request: a call that reaches one returns `waiting_permission` for a person to handle on a paired device. `create_session` refuses permission modes marked dangerous (and modes the node does not list), and `send_message` refuses sessions already in a dangerous mode, unless the server is started with `--allow-dangerous-modes` (the node's `permissions.allow_dangerous_modes` still applies); there is no session `env`. A wait follows the turn that handles the message, even when the session was busy and the message was queued behind another turn, and reports `dropped` if a queued message is cleared before it runs. Agent processes the daemon starts now carry `ANYCON_AGENT=1`; inside one, `create_session`, `send_message` and `cancel_turn` are refused unless `--allow-nested` is given. The guard against nesting is a safeguard against accidents, not a security boundary.
- Local socket clients can declare what they are with `local.set_client` (`cli` or `mcp`, a fixed set). The audit log then shows `local-mcp` for actions that came through `anycon mcp` and `local-cli` for the rest. The method is local-only; over the hub it is `forbidden`.
- Interjections that may not have been delivered. When you send a message while Codex is working and then cancel the turn, Codex can drop a message it had accepted but not yet read. The daemon now tells these apart: Codex reports when a message has been merged into the conversation, and a message still unconfirmed when the turn is cancelled is marked with a new `message_delivery { state: "uncertain" }` event (stored in the event log, so the mark is still there when you reload the history). The Web UI shows "May not have been delivered" on that message with a "Send again" button that resends the same text and attachments; the CLI prints a warning in `attach` and `history`. Nothing is resent automatically, since the message may have been read after all.
- Claude Code adapter: a "Block file writes outside the project" option (`block_outside_writes`, off by default; [ADR-48](docs/decisions.md#adr-48-claude-code文件工具不写项目外可选默认关)). When on, Write, Edit and NotebookEdit refuse paths outside the session's working directory in every permission mode, Bypass Permissions included, and the refusal shows as a notice. Shell commands are not covered. It needs Claude Code 2.1.314 or later; older versions accept the setting and ignore it. Changing it restarts the agent process before the next turn.
- When an agent withdraws a request it is still waiting on, the permission card goes away right away instead of staying until the turn ends. This happens when an MCP tool times out while its form is unanswered (Claude Code), or when Codex settles an approval itself. An answer sent after that gets `already_resolved`.
- Web UI: a Download button in the file browser's preview header saves the file to your device. It reads the file from the node in 512 KiB `fs.read` chunks and saves it as an `application/octet-stream` blob, so an HTML or SVG file is never rendered or run in the app's origin. Files up to 50 MiB; the button shows progress and cancels.
- Limit errors are told apart. The single `rate_limited` error code is split by what the user should do: `usage_limit` (the account's usage or credit limit was reached), `rate_limited` (request throttling, retry soon), `overloaded` (the provider is out of capacity, unrelated to your own usage; Codex `serverOverloaded`, `policyCapacityUnavailable`, `flexUnavailable`, and Claude Code's 529) and `budget_exceeded` (Codex's shared session token budget is used up, change Codex's own configuration). `error` events can now carry `resets_at_ms` (when the limit resets, only if the agent reported it) and, for `usage_limit`, `limit_scope` (`account` or `model`, only when the agent says which window it was; Claude Code reports its per-model weekly windows as `model`). Codex's reset time comes from its `account/rateLimits/updated` notification and is taken from the bucket of the current model; if that is ambiguous it is left out. Claude Code's `usage_limit` is read from the API error message that Claude Code marks as a usage limit (an internal field), falling back to a 429 result when the latest `rate_limit_event` is a rejection whose reset time has not passed. A Claude Code `blocking_limit`, `prompt_too_long` or `rapid_refill_breaker` result is a context-window problem and now reports `context_window_exceeded` instead of `agent_error`. The Web UI has wording for each code, shows the reset time in your local time and, for a per-model limit, suggests another model; the `rate_limited` wording is unchanged, so a web UI paired with a daemon that has not been upgraded still reads correctly (that daemon keeps sending `rate_limited` for usage limits). The CLI prints the reset time (UTC) when it follows a session. Clients that do not know the new codes fall back to showing `message`, and events already stored by an older daemon keep their old code. Protocol: [docs/protocol.md § 6](docs/protocol.md#6-会话事件).

The daemon does not offer file system or terminal access to ACP agents: they use their own tools and ask through the usual permission cards.

The ⌘K palette searches user messages and assistant replies on every selected online node through the daemon's index, next to the local title matches; picking a hit opens the session at that message and highlights it, loading older history if needed. Snippets are shown as plain text with only the matched words highlighted, and the daemon no longer keeps the control characters its snippet markers use in indexed text.

Protocol: `fs.read` takes `encoding: "base64"` and `offset`, and returns raw bytes in chunks of at most 512 KiB (`data_base64`, with the `offset` echoed), so a large image does not hold up other messages to the device.

Agent commands, directories, session `env`, preview ports, and the hub address can only be changed on the machine, and a setting fixed by an `ANYCON_*` environment variable is read-only. A request is checked as a whole, written with the file's comments kept, and audited per key. `node.logs` returns the tail of the daemon log, leaving out lines that may quote agent output. Web UI: Node settings → Limits is an editable form, and About has View logs.

A device rotates at most once a minute, and only from a connection that authenticated with its current token, so a leaked older token cannot be used to take the device over. The daemon, the Web UI, CLI devices, and the TS SDK (for identities it stores) rotate a token once it is 30 days old. SDK: `client.rotateToken()`, the `tokenRotated` event, and `onTokenRotated`. Database: migration `0004_token_rotation.sql`.

It behaves like SQLite, with row and advisory locks where SQLite relied on having a single writer; both backends share one test suite, and their migrations share numbers. `docker/compose.postgres.yml` is an example setup. Keep the `/data` volume with Postgres too (Web Push keys, admin token) and back up the database with `pg_dump`. The hub still runs as a single instance. See [docs/deploy.md § 3.2](docs/deploy.md).
- Multiple workspace roots ([ADR-45](docs/decisions.md#adr-45-多个-workspace-根)): `workspace.extra_roots` adds folders whose subfolders are projects, next to `workspace.root` (the primary root, which keeps `.scratch`). Project names stay unique across roots: linked projects win, then the primary root, then the extra roots in order. Overlapping roots, or a root inside the data directory, stop the daemon from starting; a root that is missing (an unplugged disk) is skipped with a warning and reported by `anycon doctor`. Each root has its own trash. Changing the roots needs a restart. Protocol: `node.info.workspace_roots`, `Project.root`, `TrashEntry.root`, and an optional `root` on `workspace.create` / `workspace.clone`. Only the local daemon does this; remote clients cannot. A plain `anycon export` includes everything, archived sessions too; `--project`, `--since`, `--session`, and `--exclude-archived` narrow it. The file is written with owner-only permissions and contains conversation content in plain text. Import checks the archive strictly, skips sessions that already exist, imports each session in one transaction, and rebuilds the search index. It does not keep the agent's own session id, so the next message in an imported session starts a new agent conversation while the history stays. `--dry-run` checks without writing. - Attach any file, not just images ([ADR-44](docs/decisions.md#adr-44-非图片附件落到会话工作目录)). Images still go to the model as images when the agent takes them natively. Every other attachment is copied by the daemon into the session's working directory (`<cwd>/.anycon/attachments/<session_id>/`, owner-only, created through directory file descriptors on Linux and macOS so a symbolic link swapped in by the agent cannot redirect the write), and the agent gets the relative paths, types and sizes at the end of the message text. So every agent can use every file type, and none has to ask for permission to read outside the workspace. `/.anycon/` is added to the repository's `info/exclude`, so the files never show up in `git status`. The conversation history keeps what you wrote, without that list. If the copy fails (disk full, a symbolic link in the way), the turn ends with an `attachment_failed` error and nothing reaches the agent; fix the cause and send again. Deleting a session removes its directory. Protocol: `blob.put_begin` accepts any mime (lowercased, parameters dropped; an empty or malformed one is recorded as `application/octet-stream`); only the four image types get a header check and width / height. `capabilities.attachments` lists the mimes an agent takes natively. `node.info` reports `capabilities.file_attachments` and `attachment_limits`. The per-file, per-message, and quota limits are unchanged. The Web UI adds files through the "+" menu, paste, or drag and drop (a file over the node's per-file limit is refused before it is read; against an older node it still takes images only). Files show as chips that download on click and are never rendered inline. CLI: `anycon send --file <path>` and `anycon new --file <path>`. SDK: `node.uploadFile()` and `acceptsAttachment(node, agent, mime)`; `uploadImage()` refuses a non-image mime locally. A title or preview built from attachments says `[file]` when any of them is not an image. On Windows the write is still checked first and then done by path, so a link swapped in at that exact moment is not caught.
- Windows support for `anycon` (daemon and CLI, x64, Windows 10 1809 / Server 2019 or newer; [ADR-42](docs/decisions.md#adr-42-windows命名管道job-object计划任务)). The local CLI channel is a named pipe owned by and restricted to the current user, and the CLI checks the pipe's owner before talking to it. Agents and the processes they start run in a Job Object, so stopping a session or the daemon leaves nothing behind. `~/.anycon` gets an owner-only ACL. `anycon service install` registers a per-user scheduled task that starts the daemon at logon without a console window (through the new `anyconw.exe` launcher) and needs no administrator rights; `service stop` asks the daemon to shut down cleanly first. Release archives include `anycon-x86_64-pc-windows-msvc.zip`, installed with `irm …/install.ps1 | iex`. Environment variables are matched case-insensitively on Windows, so a session `env` key like `path` can no longer stand in for `PATH`. Windows-specific system and profile directories (`AppData`, PowerShell profiles, `Program Files`, …) are on the linking deny list. Preview port detection uses the system's TCP table and the agent's job instead of `lsof`; a dev server started outside a session needs `preview.allow_ports` there.
- Web UI: the setup wizard has a Windows tab with the PowerShell installer.
- Background tasks, notices, and transient activity in the event stream ([ADR-41](docs/decisions.md#adr-41-任务快照提示和临时状态三类新事件)). Protocol: new `task`, `notice`, and `activity` events. `task` is a snapshot of a workflow, background subagent, or background command (a later snapshot with the same `id` replaces the earlier one); a workflow lists its phases and each agent's state, tokens, last tool, and error. The daemon sends at most one snapshot per task per second (status changes are never delayed) and marks tasks that were still running when the agent process went away as `cancelled`. `notice` carries non-error messages from the agent (model fallback, context compacted, rate limit, local command output such as `/context`, config and hook warnings, …) and never raises a push notification. `activity` shows what the agent is doing between outputs (retrying an API request, compacting context) until content arrives. Clients must tolerate `notice.code` values they do not know.
- Protocol: `turn_done.usage.context_window` and `context_tokens` (context window of the model, and tokens in it at the end of the turn), and `detail.url` on `kind = other` permission requests (a link the user is asked to open in a browser). All fields are optional.
- CLI: `anycon attach` / `new` / `send` print task starts and finishes, notices (a local command's output as is), and the retry / compaction status, and show the full URL of a permission request that asks to open a link. `--auto-approve` never answers such a request.
- Mock agent: the prompt keyword `tasks` emits activity, a notice, and a workflow task linked to a `Workflow` tool call; `link` asks to open a URL. `turn_done.usage` carries the context window and tokens used.
- Protocol: `Question.optional` marks a question in a `kind = question` request that may be left unanswered; the default (required) keeps `AskUserQuestion` as it was. A `completed` task can go back to `running` (a Codex sub-agent that receives new input), so clients treat the latest snapshot as the truth.
- Claude Code adapter: a workflow (including the `Workflow` tool) and background subagents and commands report their progress as tasks, with phases and each agent's state, tokens, and last tool. API retries and context compaction show as a status while the turn runs, and the context window and tokens used come with each finished turn. Notices cover a model fallback, a usage-limit warning, hook and MCP server failures, denied tool calls, and the output of local commands such as `/context` and `/cost`. An MCP server that asks for input (elicitation) is no longer cancelled automatically: its form becomes a question (fields the server does not require can be left blank) and its sign-in link becomes a permission request with the full URL.
- Codex adapter: a sub-agent is shown under the call that started it, with its state, tokens, last tool, and result, and its text and tool calls stay out of the main conversation. A running sub-agent counts as a background task, so the agent process is not reclaimed while it works. Notices cover configuration and deprecation warnings, MCP servers that failed to start, a rerouted model, declined automatic approvals, and hook failures. Context compaction shows as a status and a notice. MCP elicitation forms and links are shown like the Claude Code ones, and approving an MCP tool call offers Codex's own choices (this time, this session, always, or deny).
- Web UI: the progress of a background task sits right under the tool call that started it: a workflow lists its phases and agents, a subagent or command shows its state, tokens, and last tool. The tool line keeps showing "running in background" until the task ends, even when the call itself returned at once. A chip above the input says how many background tasks are running and lists them. Notices appear as lines in the conversation (local command output as its own block), a retrying or compacting status line shows while the turn runs, the info panel shows context usage, and permission cards show the full link with an Open button. Optional questions say so and can be skipped. Exported Markdown includes notices and the final state of each task.
- Answered questions stay in the conversation: each question is listed with its answer, and a note sent with a reply (a skip note or a denial reason) is shown under it. Protocol: `permission_resolved` carries the device's `answers` and `message`. Both fields are optional, and replies recorded before this change show the one-line summary as before.
- Claude Code background commands (`run_in_background`) show "running in background" until they finish, then get their final result and exit code. The session panel's Agents card lists them while they run and counts them as working, along with any other background tasks the daemon reports.
- Web UI: a "Recent" group at the top of the sidebar, under "Needs approval", lists the sessions that are running (running, starting, or queued), newest first, each with its project, so you no longer have to look through every project. Sessions that need approval stay in their own group and are not listed twice. Turn it off under Settings → Appearance → "Recent sessions in the sidebar" (on by default; the choice is kept per browser).
- Web UI: add a project without going to the node's home page. Use the new button next to search in the sidebar, "New project…" at the end of the project list on the new-session page, or "New project" / "Clone a repository" / "Open an existing folder" in the ⌘K palette. The dialog can switch nodes, and a project created from the new-session page is selected there.
- Web UI: Node settings → About has "Remove this node", for a machine that was reinstalled or retired. It works while the node is offline: the hub revokes the node and this browser forgets it. Revoking a node under Settings → Devices now forgets it too. Other browsers list a node removed this way under "Removed from your account" and can forget it. Projects and session history on the machine itself are not touched.
- Dev server preview ([ADR-39](docs/decisions.md#adr-39-预览-dev-servernoise-隧道里的端口转发)): open a dev server running on the daemon machine from the session page, embedded or in a new tab. The page loads on a separate preview domain (`ANYCON_PREVIEW_URL`, `https://*.aiplace.app` on the public hub) and its traffic goes through its own Noise tunnel to the daemon, so the hub still only forwards ciphertext. By default the daemon only forwards to ports opened by an agent session; other ports go in `preview.allow_ports`. Protocol: `preview.*` methods, `auth.preview_token`, `preview_peer`, and an optional `to` on `rate_limited`. Node settings gain a Preview tab that lists and closes previews. Database: migration `0002_preview.sql`.
- Hub `multi` mode (`ANYCON_MODE=multi`, [ADR-40](docs/decisions.md#adr-40-multi-模式开放注册管理员配额账号删除和-oauth-绑定)): open registration, the configuration for a public hub. The first email-code or GitHub / Google sign-in creates the account. There is no bootstrap token, token login, or invitation, and the hub refuses to start unless SMTP or an OAuth provider is configured. Admins are the accounts whose email is in `ANYCON_ADMIN_EMAILS`, plus accounts an admin has promoted. An existing `single` database can be switched to `multi`. See [docs/deploy.md § 9](docs/deploy.md#9-公共-hub-与-multi-模式).
- Per-account quotas in `multi` mode: devices, daemons, simultaneous connections, and pairing / enrollment attempts per rolling 24 hours (`ANYCON_QUOTA_DEVICES`, `_DAEMONS`, `_CONNECTIONS`, `_DAILY_PAIRINGS`; defaults 10 / 3 / 10 / 20). Every completed match costs exactly one slot: starting a pairing or enrollment counts once (`pair_begin`, `enroll_begin`), and when the node that started the pairing has no account yet (a first-time daemon), the account that pairs it pays the slot instead. A mistyped code costs nothing, and an account cannot pair fresh daemons all day. A pairing that would go over fails with `pair_failed { quota }` / `enroll_failed { quota }` and creates no device, and a connection over the limit gets `auth_fail { quota }`. Protocol: `auth_ok.quota` and `quota_update` carry the usage. The hub also serves `GET /api/quota`, and the Web UI has Settings → Quota.
- GitHub and Google sign-in (`ANYCON_OAUTH_GITHUB_CLIENT_ID` / `_CLIENT_SECRET`, `ANYCON_OAUTH_GOOGLE_…`), in both modes. Authorization code flow with PKCE and a state cookie; the callback only works on `ANYCON_PUBLIC_URL`, so the reverse proxy must pass the original `Host` (a request on another host is redirected to the public address at most once, marked `hop=1`, so a proxy that rewrites `Host` cannot cause a redirect loop). Failures, including a hub-side error (`server_error`), redirect back to the Web UI with a stable `oauth_error` code. In `single` mode new users sign up through OAuth with an invitation. Link and unlink accounts under Settings → Login methods (`GET /api/me/identities`, `DELETE /api/me/identities/:provider`). An email the provider has not verified is never used to match or create an account. The hub stores only the provider and its stable user ID, not names, emails, or tokens.
- Email-code sign-in in `multi` mode: the hub sends a code to any valid address, and entering it creates the account if there is none yet.
- Delete your account: Settings → Profile (`DELETE /api/me`, needs a sign-in from the last 10 minutes). The hub removes the account's devices, pairings, sign-in methods, and audit records, disconnects it immediately, and keeps a single `account_deleted` record. Session history on your nodes is not touched.
- Admin page: search accounts (substring of the name or email, or an exact ID; ASCII letters are case-insensitive, non-ASCII characters in a display name must match in case), grant or remove admin, and delete accounts (`GET /api/admin/accounts?q=`, `POST` / `DELETE /api/admin/accounts/:id/admin`, `DELETE /api/admin/accounts/:id`). Invitations are hidden in `multi` mode.
- Links to your terms of service and privacy policy (`ANYCON_TERMS_URL`, `ANYCON_PRIVACY_URL`, both modes, https only). When set, `/api/config` carries `terms_url` / `privacy_url`, the sign-in page shows "By continuing, you agree to the Terms of Service and acknowledge the Privacy Policy" with links that open in a new tab (only the document that is configured is mentioned), and `anycon connect` prints the same line before it sends an email sign-in code. Nothing changes when neither is set. A hub with open sign-up (`multi`) should set them; the public hub uses `https://anycon.ai/terms` and `https://anycon.ai/privacy`.
- Database: migration `0003_identities.sql` adds the `identities` and `oauth_states` tables. Migrations only move forward, so back up `/data` before upgrading if you may want to roll back.

### Changed

- Web UI: unpinning the wide-screen sidebar (the pin button next to the logo, or ⌘/Ctrl+B) leaves a narrow strip with search, new project, the number of sessions waiting for approval, and a pin button. Hovering the strip slides the sidebar out over the page, and it slides back once the pointer leaves, on a click outside, or on Esc. On touch screens, tap the strip. The "show sidebar" button in the page header is gone.
- `login_methods` in `/api/config` and `/api/me` is ordered `github`, `google`, `email`, `token`, so a `single` hub with SMTP now reports `["email","token"]`. The CLI and Web UI do not depend on the order.
- `ANYCON_ADMIN_EMAILS`, `ANYCON_QUOTA_DEVICES`, `_DAEMONS`, `_CONNECTIONS`, `_DAILY_PAIRINGS`, and `ANYCON_OAUTH_*` no longer log "recognized but not implemented". Blank values count as unset. A value that is set but invalid stops the hub from starting, in both modes. In the mode that does not use a variable it is ignored with a warning, and `ANYCON_ADMIN_TOKEN` is ignored in `multi`.
- Removing an account's last way to sign in is refused with `409 last_login_method`: unbinding the email, unlinking a GitHub / Google account, and (in `single`) deleting a login token. The three are serialized per account and judged on the account as it is inside the lock, so two requests at the same time cannot both succeed and leave the account locked out. The `single` bootstrap admin always keeps the bootstrap token.
- Web UI: the message list and the input share one column. Its text width follows the center pane, up to 72rem, with side margins that grow from 16px to 80px as the pane widens. User message bubbles are allowed up to 56rem.
- Web UI: on wide screens, the "will be sent after this turn" notice sits on the same row as the branch chip, on the left.

### Fixed

- Web UI: the sidebar no longer lists a project the node no longer has (moved to trash, unlinked, or its folder deleted). Its sessions are still on the node and open from the node's home page, search, and the project page.
- Web UI: the "Incompatible versions" and "This node no longer recognizes this device" pages have a "Node settings" button and no longer block the node's settings page, so a node that may never connect again can still be removed from the account.
- `anycon pair` on an already paired node stops as soon as the hub refuses the pairing (for example `quota` when the account's device limit is full, or the new device disconnecting) and says why, instead of waiting until the code expires and reporting a timeout. It also stops, saying so, when another pairing was started on the same node (the Web UI's Add device, a second `anycon pair`) and replaced its code. A refusal when the code is registered (the daily pairing limit, rate limiting) is no longer reported as the node being offline: `node.pair_begin` returns `busy` with `data.reason` `quota` / `rate_limited` (or `forbidden`), `unsupported` stays "not connected to the hub", and the Web UI's Add device dialog explains the quota case with a link to Settings → Quota. `--json` prints `{"failed":{"reason":…,"message":…}}` as the last line. The node keeps the outcome of the pairing it started and exposes it through the local-only `local.pair_outcome`.
- Web UI: the session info drawer no longer pops up by itself when the window is widened past 1200px and narrowed again.
- The daemon reconnects when its hub connection goes silent for 75 seconds. Before, a proxy or TUN that dropped the connection without closing it (for example Clash reloading its config) left the daemon thinking it was online while clients showed the node as offline, until the daemon was restarted.

## [0.1.1] - 2026-10-22

### Added

- Subagent tool calls are grouped under the subagent that made them, with its description, call count, state, and result. Claude Code only for now.
- The session panel shows an Agents card: the main agent and every subagent in the loaded history, with state, tokens, and tool-call count. It replaces the Options card (the same controls sit under the input) and the Files changed card (the Changes view covers it).
- Protocol: `tool_call.parent_id`, `tool_result.detail.background`, `tool_result.detail.total_tokens`, and `background_tasks` on `SessionSummary` / `SessionChanged`. All are optional, so older clients and daemons keep working.
- Web UI: drag the desktop sidebar's right edge to resize it (double-click resets it).
- Web UI: a "Block page zoom" switch under Settings → Appearance on iOS and Android. It is off by default.

### Changed

- The default `sessions.idle_timeout` is now 20m (was 10m). A `config.toml` written by 0.1.0 has `idle_timeout = "10m"` in it and keeps that value until you edit it.
- A turn the agent starts by itself (Claude Code processing finished background tasks) arrives as `turn_start` with an empty `message_id`. The Web UI marks it with a divider line.
- Web UI: on wide screens the branch chip sits above the input, on the right.
- Web UI: an option changed while a turn is running is shown in a muted color until the turn ends, instead of a hint line that shifted the layout.
- Faster connect: the Web UI sends its initial sync requests concurrently, and the hub and daemon record last-seen times off the handshake path.

### Fixed

- Claude Code background subagents and commands are no longer killed when `idle_timeout` reclaims the agent process. Reclaim, `session_idle`, and the `turn_finished` notification wait until they finish.
- Re-pairing a revoked device no longer fails with "the code is wrong or has expired". The browser no longer sends the old node link's IK into the new pairing handshake.
- Pairing no longer stalls when the hub bounces a handshake envelope under backpressure. The daemon now resends it.
- Codex: the model set in `~/.codex/config.toml` shows up as an option even when `model/list` omits it (common with a custom `model_provider`).
- Question cards show a single submit button, and it sends the collected answers.
- The SDK no longer matches an agent-started turn to a `send()`.

## [0.1.0] - 2026-10-18

First public release.

### Hub (`anycon-hub`)

- Single-tenant (`single`) mode with admin-token login and invite links. It runs as one container and one SQLite file, with an embedded Web UI.
- Device authentication, routing, and pairing / enrollment matchmaking. The hub only relays end-to-end encrypted envelopes and sees metadata.
- Web Push, email-code login for accounts with a bound email, and SMTP email notifications.
- `/healthz`, `/readyz`, strict CSP, and rate limiting. Ready-made reverse-proxy configs for Caddy, nginx, Traefik, and Cloudflare Tunnel.

### Daemon and CLI (`anycon`)

- Outbound connection to the hub, with reconnect, sleep recovery, and launchd / systemd user services.
- Noise XX+psk3 pairing with locally generated codes (Argon2id-stretched) and Noise IK reconnects.
- Account enrollment: node password, QR approval, and one-time enrollment codes (CPace).
- Claude Code and Codex adapters, agent detection, and per-session model / reasoning / permission-mode settings.
- Permission requests answered from any paired client, with a local audit log.
- Workspace: every folder is a project. Create, clone, rename, trash and restore projects, or link existing directories.
- Per-session git worktrees: diff, sync with base, archive / delete handling, PR status, and auto-archive.
- Image attachments.
- CLI clients: `connect`, `new`, `send`, `attach`, `approve`, `diff`, `sync`, `worktrees`, and more.

### Web UI

- Streaming chat with tool-call rendering, thinking blocks, diffs, permission cards, and image attachments.
- Worktree workflow: changes tab, branch chip, base sync, and PR status.
- Node and account settings, notifications, IndexedDB cache, installable PWA, English and Chinese.

### SDK

- `@anycon/protocol` (generated types, envelope and JSON-RPC codecs, Noise wasm) and `@anycon/sdk` (client direction, image upload).

### Distribution

- Hub image `ghcr.io/anycon-ai/hub` for linux/amd64 and linux/arm64.
- `anycon` binaries for macOS (arm64, x64) and Linux (x64, arm64, glibc 2.35+), installable with `brew install anycon-ai/tap/anycon` or the release's `install.sh`, with SHA-256 checksums and build provenance.
- `@anycon/protocol` and `@anycon/sdk` on npm, published with provenance.
- Every artifact ships its third-party license notices.
